## 2. 交叉审查抓到的真问题（按影响排序）

会导致**结论错误**的（最有价值）：
- **#10** Godot 的 `Vector2` 是 32 位浮点，计数器不是注释声称的 64 位
- **#10** 只用尺子测「证明不了原始计数」，例如固定丢 0.5% 也能通过 → 促成了独立 Raw Input 基准
- **#16/#20** 比对脚本的 5 种「误判通过」：重启后轮号重复掩盖失败、重复右键虚增样本、无移动也算通过、时间就近配对有歧义、重复输入同一文件
- **#20** 基准监听全系统点击而 Godot 只收自己窗口 → 改为毫秒时间戳配对
- **#24** 测量起点用「动画开始」代替「按键」会带来固定偏差；OBS 游戏采集、向 CS2 目录放文件与红线冲突

会导致**结论夸大**的：
- **#20** 报告写「无丢失、无取整」，但数据只支持「已测条件下每轮累计值一致」
- **#24** 把录像采样间隔当成测量精度

工程与规范：
- **#6** 共享文件夹两个 agent 并发认领的竞态 → 用 `task/<号>` 分支作为原子锁
- **#13** 路线图依赖倒置（M2 依赖 v1.0 才有的靶场）
- **#23** JSON 数据导出时默认不会被打包

## 3. 漏掉或绕了弯路的

- **测试对人不友好**：P0-4 第一版测试步骤太复杂，测试人两次没能完成，直到加了屏幕引导才顺利。教训：**需要人参与的验证，交付物是「人能做完的流程」，不是「正确的步骤文档」**
- **Codex 第 2 轮才发现系统级点击的问题**：第一版设计时没有想到测试人会在别的窗口操作。教训：设计验证工具时，要先写出「测试人实际会怎么操作」
- **PowerShell 踩坑**：评论正文里的引号导致 `gh` 参数被拆开（改用 `--body-file`）；`Set-Content -Encoding utf8` 会写 BOM（改用 .NET 无 BOM 写法）
- **更新日志反复冲突**：多个 PR 同时往同一处追加 → 已规定单组小节、追加到末尾；仍会冲突，但很好解决

## 4. 分工效果

| 任务类型 | 谁效果最好 | 观察 |
|---|---|---|
| 找逻辑漏洞、找「误判通过」 | GPT | 几乎每轮都能给出可复现的反例，这是最大的价值 |
| 数值复算、事实边界 | GPT | 对没核实的内容会主动降级为「待测量」，有时过于保守 |
| 架构、流程、给人用的体验 | Claude | 引导模式、输入显示层这类「让人能做完」的设计 |
| 领域经验（CS 手感、社区公式） | Claude | 作为先验提供，但必须标注「未核实」 |
| 命名、文案 | Gemini | 风格统一、主动避开现有点位名；严格遵守了协议（发现主文件夹有改动就停下） |

## 5. 协作开销是否值得

- 审查轮数：Claude 的 PR 平均约 2–3 轮，P0-4 相关的 #10、#20 各 4 轮
- 主观判断：**值得**。P0-4 是项目最大的技术风险，如果比对脚本带着「误判通过」的漏洞，我们会得到一个看起来很漂亮但不可信的结论
- 成本：每轮 Codex 审查约 3–8 分钟；交接全部留在 GitHub 上，回看成本低
- 待人类补充：从你的角度，等待合并的次数和频率是否可以接受？

## 6. 下个版本的调整（提议）

1. **验证类工具先写「测试人怎么操作」**，再写代码；需要人参与的流程默认做成引导式
2. **报告类文档提交前，作者先自查「结论是否超出数据」**（这次被抓了两次）
3. 继续「GPT 审 Claude」为主；Gemini 增加调研类任务（#1），观察长文调研的质量
4. 引入 CI（ADR 0002）后，审查可以把精力从「测试是否通过」转向「逻辑是否正确」
5. 待讨论：小的文档类 PR 是否可以一轮审查通过后由 Claude 直接合并，减少人类等待（需要人类决定）
