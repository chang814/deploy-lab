# 0003 · 合并权限：降低人类批准频率，以更多审查交换

- 状态：提议（须人类批准）
- 日期：2026-11-26
- 关联：Issue #29、PR #30；规则正文在 `docs/02-workflow.md`「合并权限」；总开关 Issue #31

## 背景

Phase 0 的两天里，每个 PR 都要等人类说「批准合并」，人类成了流程中最慢的一环。产品负责人决定：**批准频率再低一点，Claude 可以多自主决定，多些审查即可**；小的文档类 PR 一轮审查通过后可以直接合并。

把合并权交给作者方（Claude）的风险是：Claude 可能在规则字面上合规，却绕开人类本该把关的事。GPT 用「找漏洞」的角度审了两轮，第一轮找出 8 种绕法，第二轮又找出 4 种。

## 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 维持现状，每个 PR 都由人类批准 | 最安全 | 人类负担重，节奏慢；人类也未必有时间逐个细看 |
| **B. 分级授权：大部分 PR 由 Claude 合并，以更严格的审查与审计交换；高风险类别保留给人类** | 节奏快；人类只看真正需要人判断的事 | 规则复杂；有被钻空子的风险，需要靠规则本身与审计来防 |
| C. 完全交给 Claude | 最快 | 红线、产品方向、验收标准都失去人类把关，不可接受 |

## 决定

选择 B。要点：
1. **人类保留**：红线、产品方向、发布、决定性结论、流程与审查规则（含提示词）、验收标准（CI 与测试设施、放宽测试）、不可撤销操作、被标记或僵持的 PR
2. **审查加码**：审查绑定最终提交与最新 main；代码类须复审确认；核心或大功能加一次独立的 Codex 会话审查；方式 A 中调度者视为作者；使用标准审查提示词且只能加不能减
3. **不能洗掉历史**：审查轮数与阻塞意见按 PR 累计，替代 PR 继承；人类批准同样绑定提交
4. **人类随时可收回**：总开关 #31、`needs-human` 标签、每轮对话结束时汇报、每次合并留审计记录

## 后果

- 人类批准的次数会明显减少；每次需要人类时，都是规则明确划出的高风险事项
- Claude 的每次合并都有可追溯的审计记录，人类可以事后抽查
- 规则目前靠 Claude 自觉执行。将来可以用 GitHub 分支保护强制其中一部分（例如必需的 CI 检查、必须是最新 main），这属于改仓库设置，须人类决定
- 下次复盘时评估：自主合并中有没有出过问题、人类抽查的结果、规则是否过严或过松
