# 多 agent 工作流（v0 草案）

> 这是一份会持续修改的文档。每个版本结束后，根据复盘结果更新它。

## 角色

| 角色 | 执行者 | 擅长 / 负责 | 不负责 |
|---|---|---|---|
| 产品负责人 / 验收人 | 人类 | 拍板、优先级、**主观手感测试**、账号与发布操作 | — |
| 技术负责人 / 集成 | Claude（Claude Code） | 架构、视角与动画手感调校、视觉审美、任务拆分、合并前把关 | 单独决定产品方向 |
| 严谨实现 / 审查 | GPT（Codex CLI） | 数学与换算、输入管线、状态机、单元测试、**交叉代码审查** | 美术方向 |
| 文案 / 调研 | Gemini（Antigravity） | README、更新日志、Release 说明、游戏内文本、长文档调研总结 | 核心代码 |

## 核心原则

1. **一家写，另一家审。** 任何合入 `main` 的 PR 都必须经过「非作者」模型的审查。谁可以按下合并，见下文「合并权限」。
2. **GitHub 是唯一事实来源。** 任务 = Issue，改动 = PR，讨论留在 Issue/PR 里，不留在某个聊天窗口里。
3. **共享同一份规范。** 三家的说明文件（`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`）只写各自角色差异，通用规则统一引用 `PROJECT_RULES.md`。
4. **能测的不靠感觉。** 灵敏度、时长等指标必须有自动化测试或测量数据；只有「像不像」交给人类主观判断。

## 一个任务的生命周期

```
Issue（人类或 Claude 创建，打角色标签 owner:claude / owner:gpt / owner:gemini）
  → 分支 task/<issue号>（在 .worktrees/ 中，见 05-shared-folder-protocol.md）
  → 作者 agent 实现 + 自测
  → PR（模板里写：做了什么 / 怎么验证 / 风险）
  → 交叉审查（另一家模型，输出结构化审查意见）
  → 作者修改（必要时多轮）
  → 按「合并权限」：Claude 自主合并，或等待人类批准 → Squash 合并
  → 里程碑结束：Gemini 起草 CHANGELOG / Release 说明 → Claude 校对 → 打 tag → GitHub Release
```

## 调度方式

有两种方式，按任务选择：

| 方式 | 怎么做 | 适用 |
|---|---|---|
| **A. Claude 调度** | Claude 在命令行调用 `codex exec`：审查用 `--sandbox read-only`；写作用 `--sandbox workspace-write -C <worktree>`，由沙箱参数限制 Codex 只能写该 worktree，提示词中也要求它不联网、不提交。交接规则见下文 | GPT 的审查和实现任务（默认） |
| **B. 人类启动** | 人类在对应工具里打开项目，粘贴 `docs/prompts/` 下的提示词，agent 自己按协议认领、提交、提 PR | Gemini（经 Antigravity，见 `docs/prompts/gemini-kickoff.md`）；人类想直接观察时的 Codex（见 `docs/prompts/codex-kickoff.md`） |

**方式 A 的交接规则（Codex 写作时）：**
1. 由 Claude 创建 worktree 并在 Issue 下留言「认领：gpt（由 claude 用 codex exec 调度），worktree …」。这个 worktree 只属于这一次调度
2. `codex exec` 是同步运行的：Codex 进程运行期间，Claude 不读写、不暂存这个 worktree
3. Codex 进程退出后，Claude 才检查改动、提交（记为 `Agent: gpt (dispatched by claude via codex exec)`）、推送、提 PR，并把 Codex 的汇报贴进 PR
4. 审查改为由 Claude 进行；需要修改时，再调度一次 Codex 在同一个 worktree 中修改，重复 2–3

- Gemini CLI 的个人 Google 账号登录已被停用（2026-11），所以 Gemini 目前只能用方式 B。
- **并行：** 只要各自在不同的 `task/<号>` worktree 里，多个 agent 可以同时工作。人类也可以另开 Codex 会话认领独立的 Issue 与 Claude 并行。分配原则：同一时间同一组文件只有一个写入者；有依赖关系的任务不并行。

## 合并权限

产品负责人决定（2026-11-26）：**降低人类批准合并的频率，由 Claude 自主合并更多 PR，以更多的审查作为交换。** 决策记录见 [ADR 0003](decisions/0003-merge-authority.md)。

本节的设计目标：Claude 不能在规则字面上合规、却绕开人类本该把关的事。下面每条规则后的括号写明它防的是哪种绕法。

### 0. 总开关与合并前检查

- **总开关：** 仓库里有一个置顶的 Issue「自主合并总开关」（#31）。人类给它打上 `automerge-paused` 标签，或在对话中说「暂停自主合并」，所有自主合并立即停止，直到人类取消。（防：人类只能逐个 PR 收回权限）
- **每次自主合并前**，Claude 必须重新检查：总开关未暂停；PR 和关联 Issue 都没有 `needs-human` 标签；PR 中没有未关闭的阻塞意见。任一不满足就不合并。**读取不到这些状态（例如网络错误）时，视为不满足**，不合并。
- 人类在对话中说「暂停自主合并」时，Claude 立即给 #31 打上 `automerge-paused` 标签，让其他会话也能看到。

### 1. 必须由人类批准的 PR（任何一条命中即是）

| 类别 | 例子 |
|---|---|
| 红线相关 | 修改 `PROJECT_RULES.md`；引入第三方素材或依赖（许可证）；任何接触 CS2 文件或进程的代码 |
| 产品方向与范围 | 立项书（`docs/00-charter.md`）；路线图的里程碑、范围或顺序；手感目标与验收指标；产品命名 |
| 发布 | 打 tag、发布 GitHub Release、改版本号 |
| 决定性结论 | 对「能不能用 / 要不要换方案」下结论的报告（例如 spike 报告的最终判定） |
| **规则与审查本身** | 本节；`docs/05-shared-folder-protocol.md`；三家 agent 的说明文件；**`docs/prompts/` 下所有提示词**（它们决定 agent 怎么干活、怎么审查）（防：先放松审查提示词，再用放松后的审查放行别的改动） |
| **验收标准本身** | `.github/workflows/` 下的 CI 配置；测试入口 `tests/run_all.gd`、`tests/test_case.gd`、`tests/runner_fixtures/`；**删除、跳过或放宽任何已有测试**（防：把测试换成 `echo ok`，CI 照样绿）。只**新增**测试、不动已有测试和测试设施的 PR 不在此列 |
| 不可撤销或影响外部 | 删除数据、改仓库设置或权限、改 CI 的密钥与权限 |
| 被要求的 | 人类给 PR 或 Issue 打了 `needs-human` 标签；作者或任何审查者在评论中写明「需要人类决定」 |
| 审查僵持 | 同一个 PR 累计三轮审查仍未「通过」（见 §4，换审查会话不清零） |

**不能自我批准：** 修改本节的 PR 不能按它自己带来的新规则合并，只能按合并前 `main` 上的规则处理（实际效果：一律要人类批准）。

**人类批准也绑定提交：** Claude 请求批准时写明当前提交 SHA（前 7 位即可），人类的批准只对这个提交有效。之后再有任何提交，必须重新请求批准。（防：人类批准 A 后推送扩大改动的 B，再引用对 A 的批准）

### 2. 分类：按实际效果，不按目录

- PR 按它**实际改变了什么**归类，不按文件放在哪个目录。例如：改变 agent 行为的提示词不是「说明性文档」；会被代码读取的 JSON 是代码类
- **混合 PR 从严**：只要有一处属于代码类，整个 PR 按代码类；只要有一处命中 §1，整个 PR 要人类批准
- **拿不准就从严**：未列出的文件类型、配置、资源文件，一律按代码类
- 文档类仅指**只给人读、不被任何程序或 agent 当作输入**的内容

### 3. Claude 可以自主合并的 PR

不属于 §1 的 PR，满足以下条件后由 Claude 合并：

| 类型 | 合并前必须满足 |
|---|---|
| **文档类** | ① 非作者审查，**针对最终提交**结论为「通过」；② 最终提交的 CI 通过 |
| **代码类** | ① 非作者审查**直到某一轮针对最终提交结论为「通过」**：「修改后通过」不算，修改后必须再审一轮确认；② 最终提交的 CI 全部通过；③ 命中「加审」条件时，加审也针对最终提交「通过」 |

**审查绑定最终提交：** 每条审查结论都要写明它审查的提交 SHA。审查之后只要再有任何提交（包括「只改了个注释」），之前的「通过」就失效，必须对新提交再审一轮（可以只审新增的差异，但结论要写新 SHA）。（防：A 审完通过后推送改变行为的 B，再引用 A 的通过合并）

**也绑定目标分支：** 合并时分支必须包含当前最新的 `main`（GitHub 上不能显示「落后于 main」）。如果审查或 CI 之后 `main` 又前进了，先把最新 `main` 合并进分支，这会产生新提交，于是按上一条重新审查（重点看集成后的行为）并重新跑 CI。（防：在旧 main 上通过的结果，合并到已经变化的 main 上出错）

**标准审查提示词：** 自主合并所依据的审查，必须以 `docs/prompts/review-standard.md` 为基础，再加上本次的具体关注点；只能在标准内容上**增加**要求，不能删减或放宽。PR 评论中贴出实际使用的完整提示词。（防：通过改写调用指令让审查变松）

**加审（代码类）：** 满足任一条件时，在常规审查通过后，再开一个**全新的 Codex 会话**，只做一件事：寻找会让测试或 CI「误判通过」的漏洞和常规审查没覆盖的边界情况：
- 改动涉及 `src/core/` 或输入管线
- 同一个**功能**累计改动超过 300 行（新增 + 删除，不计 Godot 自动生成的 `.uid` 文件）。「同一个功能」按路线图上的条目算（例如「v0.1 基础移动与碰撞」），不论拆成几个 Issue、几个 PR，都合并计算；拿不准属于哪个功能时，按更大的范围算（防：把一个功能拆成多个 Issue 或多个 290 行的 PR）
- 方式 A 调度的 GPT 代码（见下条）

**独立性：** 作者不能当自己的审查者，**实质贡献了设计的调度者也算作者**。具体：
- Claude 写的：由 GPT 审
- GPT 写的（方式 A，Claude 调度）：Claude 通常给出了实现方案，所以 **Claude 的审查不能单独作为合并依据**，必须再有一个没参与实现的全新 Codex 会话审查通过（防：Claude 设计、GPT 照写、Claude 自审、Claude 自合）
- Gemini 写的：由 GPT 审

### 4. 审查历史累计，异议必须逐条关闭

- 一个 PR 的审查轮数**累计计算**，换审查会话、换模型都不清零（防：一直换会话直到有人说通过）
- **替代 PR 继承历史：** 关闭一个 PR 后，又用新 PR 提交相同或相近的改动时，新 PR 必须在描述中链接旧 PR，并继承旧 PR 的审查轮数、未关闭的阻塞意见和「需要人类决定」的要求。关闭还有未关闭阻塞意见的 PR 时，要在关联 Issue 中写明原因（防：关掉旧 PR、重开一个干净的新 PR）
- 任何一轮提出的「必须修」，都要在 PR 中逐条列出处理结果，并由**后续一轮审查明确确认已解决**，才算关闭。有未关闭的阻塞意见时不能合并
- 不同审查者结论冲突时，以更严格的为准；无法消除的分歧交给人类

### 5. 人类如何保持知情

- **每次自主合并**，Claude 在 PR 下留一条审计记录，打上 `merged-by:claude` 标签。记录包括：
  - 分类和依据（§2、§3 的哪条）
  - 最终提交 SHA 与合并时 `main` 的 SHA
  - 各轮审查评论的链接，以及阻塞意见的关闭情况
  - 最终提交的 CI 运行链接
- **只要这一轮对话中自主合并过 PR，Claude 就在这一轮结束时向人类列出**：合并了哪些、各自一句话说明（不攒到「定期」再说）
- 人类可以随时：用 §0 的总开关暂停全部自主合并；给单个 PR 或 Issue 打 `needs-human`；要求回滚某次合并（回滚也走 PR，不强推 `main`）
- 以后可以考虑用 GitHub 的分支保护强制执行一部分规则（例如必需的 CI 检查）。这属于改仓库设置，须人类决定
